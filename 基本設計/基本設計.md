# 本ノートの目的
[[Utilities/Documents/要件定義/要件定義|要件定義]]を実現するための、システム全体の構造・実行方式・共通ルールの方針を定める。個別の設定値・関数仕様は[[スポット/Pythion開発/（旧）共通設定・モジュール仕様|詳細設計]]配下の各ノートを参照。
# システムの開発方針
- 汎用機能を持たせるモジュール群と、個別タスクを処理するスクリプトの2種を実装すること。
- モジュールは各タスクで使い回せるようにすること。
- タスクを追加した際に、既存タスク・モジュールとの不整合を出さないこと。
- バッチ処理と、個別に手動で実行するタスクの両方に対応できるようにすること。
- ローカルで実行可能な処理はPythonで行い、AIへの問い合わせは最低限に留めること。
- AIに問い合わせを行う際はリクエストの回数をできるだけ減らすこと。
- 今後のタスク追加・改修のために、ソースコードとともに仕様書を作成すること。

# 開発共通ルール
## 実行方式（CLIエントリーポイント）
本システムはHTTPサーバー等の常駐プロセスを持たず、`main.py`を**CLIエントリーポイント**として実行する。Obsidianからのリアルタイム実行時も、ターミナルから`main.py`に引数を与えて呼び出す運用とする（FastAPI等のWebフレームワークは導入しない）。

- タスク実行は `--task 個別タスク名` で指定し、`config/tasks/個別タスク名.yaml` と名前を一致させる。
- タスクに実行日が必要な場合は、 `config.yaml` の `run.target_date_source` から取得する。
	- `arg`：コマンドライン引数（例：`--date 2026-07-30`）から取得
	- `env`：環境変数から取得
	- `auto`：実行日から自動算出
- 実行モード（dry_run / execute）は `--mode dry_run` / `--mode execute` のコマンドライン引数で指定する。引数省略時は `config.yaml` の `run.mode` の値をデフォルトとして使用する（詳細は次項「実行モード（dry_run / execute）の共通挙動」を参照）。
- バッチ実行（Powershell + タスクスケジューラ）・手動実行のいずれも、同一の`main.py`・同一の引数体系で処理できるようにすること。

実行例：
```bash
# 手動実行（dry_runで内容確認）
python main.py --task daily_transfer --date 2026-07-30 --mode dry_run

# 手動実行（内容を確認した上で本番反映）
python main.py --task daily_transfer --date 2026-07-30 --mode execute

# バッチ実行（PS1から呼ぶ場合も同じ引数体系。--mode省略時はconfig.yamlのrun.modeに従う）
python main.py --task daily_transfer --date auto
```
## 実行モード（dry_run / execute）の共通挙動
実行モードは、コマンドライン引数`--mode dry_run` / `--mode execute`で指定する。引数省略時は`config.yaml`の`run.mode`を使用する。バッチ実行では原則として`--mode`を明示する。
- `dry_run`：AI問い合わせ、キャッシュ判定、対象抽出、変更内容の生成まで通常どおり実行するが、ファイルへの書き込み、スナップショット取得、移動、削除は行わない。
- `execute`：入力および対象状態を再評価し、競合がないことを確認した上で、スナップショット取得後に実際の書き込みを行う。
`dry_run`は実行時点の変更予測であり、後続の`execute`結果を固定しない。入力ノート、参照ノート、設定、プロンプト、モデル、キャッシュ、転記先等が変化した場合、両モードの結果が異なることを許容する。
## 実行日・対象日の解決
タスクが実行日を必要とする場合、`run.target_date_source`に従って解決する。
- `arg`：`--date`を必須とする。未指定または不正な場合はERRORとしてタスク開始前に中断する。
- `env`：所定の環境変数を必須とする。未設定または不正な場合はERRORとしてタスク開始前に中断する。
- `auto`：`run.timezone`の現在日時から日付を算出する。
日付形式、タイムゾーン、取得元が不正な場合、システム日付等へ暗黙にフォールバックしてはならない。
## 設定ファイルの読み込み・マージ順序
設定は以下の3層で管理し、後に読み込んだ層を優先する。
1. `config/config.yaml`（全システム共通）
2. `config/project_types/プロジェクト別ファイル名.yaml`（プロジェクト別）
3. `config/tasks/個別タスク名.yaml`（タスク別）
タスクが複数プロジェクトを横断する場合、プロジェクト別設定の読み込みとマージはプロジェクトごとにやり直す。
### マージ規則
- スカラー値：後勝ちで置換する。
- 辞書：キー単位で再帰的にマージする。
- 配列：後勝ちで配列全体を置換する。自動結合しない。
- `null`：明示的な値として後勝ちで置換する。キー削除の意味には使用しない。
配列を結合する必要がある設定項目は、個別仕様で専用の結合規則を定義する。共通マージ処理が配列を推測して結合してはならない。
どの設定項目をどの層へ置くかは、次を基準とする。
- 複数タスクで共通し、`project_type`ごとの規約に依存する値：プロジェクト別設定
- タスク固有の実行時挙動：タスク別設定
## AI使用フラグの共通挙動
- `ai_check: false`：プロジェクト自体を自動処理対象から除外する。
- `ai_check: true`かつ`use_ai: false`：ローカル解析のみ実行し、解決できない対象はスキップする。AIへフォールバックしない。
- `ai_check: true`かつ`use_ai: true`：ローカル解析を優先し、個別仕様で許可された場合のみAIへフォールバックする。
## モジュール群の実装
モジュールは、各タスクで共通して用いる汎用モジュール群と、`project_type`毎に異なる規約（フォルダ配置、タグ構造など）に依存する処理を行うプロジェクト別モジュールの2層に分けて実装する。

- `modules/`
	- `汎用モジュール名.py`（[[#詳細設計ノート一覧]]参照）
	- `project_types/`
		- `プロジェクト別ファイル名.py`（[[#詳細設計ノート一覧]]参照）

なおプロジェクトタイプ別モジュール群は、汎用モジュール群を内部で利用する側であり、置き換えるものではない。
## `project_type`とファイル名のマッピング
ファイル名の文字化けを避けるため、プロジェクト管理ノートの`project_type`の値（例：`執筆`）は日本語で運用しつつ、`config.yaml`の`project_type_mapping`でそれに対応するファイル名（半角英数）を指定する。
このマッピング表を元に、
- `config/project_types/プロジェクト別ファイル名.yaml`
- `modules/project_types/プロジェクト別ファイル名.py`
を動的にインポートする。
```yaml
project_type_mapping:
  "執筆": "writing"        # project_types/writing.py を読み込む
  "デスク環境": "desk_env"  # （将来）project_types/desk_env.py
```

各タスクスクリプトは、プロジェクト管理ノートの`project_type`を読み取り、上記マッピングでモジュール名を解決した上で該当モジュールをロードすること。新しい`project_type`を追加する際は、このマッピングに1行追加するのみとし、`taskscripts/`側の分岐を増やさないこと。
## 個別タスク用ファイル命名ルール
個別タスクに関する以下のファイルは、名前を一致させること。
- `Utilities/Python/taskscripts/個別タスク名.py`（タスクごとの処理）
- `Utilities/config/tasks/個別タスク名.yaml`（タスク別設定）
- `Utilities/Python/prompts/個別タスク名.txt`（ AI問い合わせ用のプロンプトテンプレート）
## Markdownファイル処理ルール
- Frontmatterの要素と順番を壊さないこと。
- ノートのMarkdown構造（見出し・箇条書きの階層など）を崩さず、データの一貫性を保つこと。
- アルファベット・数字は原則として半角で統一すること。既存ノートに全角英数字（例：`Ｐｙｔｈｏｎ`、`ＡＩ`）が混在している場合も、編集時に半角へ統一する。
## 参照リンク（wikilink)
同名ノートが複数フォルダに存在する場合でもリンク先が一意に定まるよう、原則としてフルパス形式を用いること。（ただしモジュールで切り替え可能にはしておく）
## 競合更新の検出
ファイル読込時に少なくとも`updated`、ファイル最終更新時刻、ファイルサイズを記録する。書き込み直前に対象ファイルを再確認し、読込時から`updated`が変わっている場合は競合として書き込みを中止する。競合時に最新内容との自動マージは行わない。
## 複数ファイル更新の一貫性
1つの転記ブロック等を1つの処理単位として扱う。
1. 転記元と転記先の競合を確認する。
2. 更新対象全ファイルのスナップショットを取得する。
3. 転記先を書き込み、再読込して成功を検証する。
4. 転記元を書き込み、再読込して成功を検証する。
5. すべて成功した場合のみ処理完了とする。
途中で失敗した場合、安全に復元できるときは処理単位全体を復元する。復元前に競合を検出した場合は自動復元せず、スナップショットの場所をログへ記録して中断する。
