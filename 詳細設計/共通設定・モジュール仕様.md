# 本ノートの目的
[[Utilities/Documents/基本設計/基本設計|基本設計]]の開発方針にある「汎用機能を持たせるモジュール群」、および全システム共通の設定ファイルの詳細をまとめる。
`project_type`ごとの設定ファイル・モジュールの詳細は、本ノートではなく[[Utilities/Documents/基本設計/基本設計#詳細設計ノート一覧|詳細設計ノート一覧]]の各仕様書を参照せよ。
# 設定ファイル（`config/`以下）
## .env
`ANTIGRAVITY_API_KEY`、`GEMINI_API_KEY`を書く。
（将来Gemini直接呼び出しに変わる場合に備えて分離しておく）
## config.yaml
各スクリプト共通設定として、以下を書く。
```
# --- Vault の基本設定 ---
vault:
  path: "D:/OneDrive - 藤春都/Obsidian"

# --- デイリーノートのフォルダ ---
daily_folder: "DailyNote"

# --- プロジェクトタイプ別ファイルのマッピング ---
# project_type（日本語）→ project_types/以下のファイル名（半角英数）の対応表。
# 新しいproject_typeを追加する際は、ここに追加する
project_type_mapping:
  "執筆": "writing"        # project_types/writing.py・writing.yaml を読み込む
  "デスク環境": "desk_env"  # （将来）project_types/desk_env.py・desk_env.yaml

# --- 除外対象フォルダ ---
exclude:
  folders:
    - "copilot"
    - "Utilities"
    - "Web Clipper"
    - "スポット"

# --- AIセクション ---
ai:
  provider: "antigravity"            # Antigravity経由かGemini直接かを明示
  agent: "gemini_3.1_flash-lite"
  timeout_sec: 15
  retry:
    max_attempts: 3
    backoff_sec: 5                   # リトライ間隔（指数バックオフなら base値）
  rate_limit:
    on_exceed: "queue"               # "queue" / "skip" / "abort"
    max_wait_sec: 60
  cache_enabled: true
  cache_folder: "cache"
  cache_ttl_days: 3                  # キャッシュの有効期限
  temperature: 0.2
  prompt_template_folder: "prompts"  # プロンプトテンプレート置き場（Python/配下からの相対パス）

# --- 実行制御セクション ---
run:
  mode: "dry_run"            # "dry_run" / "execute"（--mode省略時のデフォルト。--modeで上書き可）
  target_date_source: "arg"  # "arg"（PS1から引数）/ "env"（環境変数）/ "auto"（実行日から自動算出）
  timezone: "Asia/Tokyo"

# --- ロギングセクション ---
logging:
  level: "info"            # "debug" / "info" / "warning" / "error"
  log_skip_reasons: true   # スキップ理由を必ず記録するか
  log_folder: "logs"
  rotate: true
  retention_days: 14       # ログ自体の保持期間（backup.retention_daysと分離）

# --- バックアップ・スナップショット ---
backup:
  retention_days: 3
  on_write_failure: "restore_from_snapshot"   # "restore_from_snapshot" / "manual"
  snapshot_folder: "snapshots"

# Markdownのフォーマット
markdown_format:
  indent_style: "tab"  # "tab" または "space4"
  tab_width: 4         # タブ1個をスペース何個相当として深さ判定するか
  line_ending: "crlf"  # "crlf" または "lf"
  encoding: "utf-8"    # BOM付きにするか運用で統一
  bom: false
  wikilink_style: "full_path_no_ext"  # Wikilink生成形式

# --- Markdown書き戻し関連 ---
markdown_processing:
  scope: "block_only"               # "file"（ファイル全体にmdformat適用） / "block_only"（追記ブロックのみ整形して差し込む）
  apply_to_existing_content: false  # 既存の未変更部分にはmdformatをかけない
  formatter_options:
    wrap: "no"
    number: false
  frontmatter:
    sort_keys: false                # Frontmatterのキー順を維持
    preserve_quote_style: true
```
`project_type`別・タスク別の設定ファイルの実際の内容は、本ノートではなく各`project_type`の仕様書・各タスクのノートを正とする（読み込み・マージ順序は[[Utilities/Documents/基本設計/基本設計#設定ファイルの読み込み・マージ順序|基本設計]]参照）。
# モジュール概要
モジュールは`Utilities/Python/modules/`以下に、機能ごとにpyファイルを作成する。
各タスクスクリプト（`taskscripts/`以下）は、本ノートに定めるモジュールを通じて共通処理を呼び出し、タスク固有の判定ロジックのみを個別実装すること。

スクリプトの動作環境は[[Utilities/Documents/詳細設計/Python実行環境・AIエージェント情報|Python実行環境・AIエージェント情報]]を参照せよ。
# 汎用モジュール一覧
以下は、`project_type`を考慮しない汎用モジュールである。

| モジュール名                             | 想定ファイル名             | 概要                                                                                     |
| ---------------------------------------- | -------------------------- | ---------------------------------------------------------------------------------------- |
| プロジェクト探索モジュール               | `project_discovery.py`     | 指定条件を満たすプロジェクトを検出し、プロジェクト名等の基本情報を取得する               |
| Markdown / Frontmatter入出力モジュール   | `markdown_io.py`           | Markdown構造・書式を保持しつつ、ノートの読み込み・書き戻しを行う                         |

| 箇条書きタグツリー解析・追記モジュール   | `markdown_tag_tree.py`     | インラインタグ付き箇条書きツリーの抽出・追記・削除を行う                                 |
| AI問い合わせモジュール                   | `ai_client.py`             | AIへの問い合わせ、ローカル処理優先の切り替え、出力形式統一、エラー時フォールバックを行う |
| キャッシュモジュール                     | `cache.py`                 | AI解析結果のキャッシュ管理を行う                                                         |

## プロジェクト探索モジュール（`project_discovery.py`）
`project_type`を問わず、指定した条件を満たすプロジェクトを検出する処理を共通化する。
（`project_type`・`status`・`ai_check`・`project_name`はいずれも全プロジェクト共通のFrontmatterフィールドのため、`project_type`ごとのモジュールではなく本モジュールに実装する。[[Utilities/Documents/詳細設計/データ整理ルール#Frontmatterパラメータ定義|データ整理ルール]]参照）。
### `find_projects(project_type, status=True, ai_check=True)`
1. Vault直下のプロジェクトフォルダ候補を走査する。
2. フォルダ直下から、フォルダ名と同名かつ `type: プロジェクト管理ノート` のノートを取得する。
3. Frontmatter検証モジュールを用いて、 プロジェクト管理ノートとしての必須項目を検証する。
	1. `project_type`、`status`、`ai_check` が引数で指定された値と一致するプロジェクトを抽出する。
4. 条件に一致したプロジェクトについて、 `project_name`、プロジェクトフォルダのパス、 プロジェクト管理ノートのパスを返す。
5. Frontmatterに不備がある場合は、 警告またはエラーをログに記録し、 当該プロジェクトを処理対象から除外する。
## Markdown / Frontmatter入出力モジュール（`markdown_io.py`）
ノートの読み込み・書き戻しに関する共通処理を担う。
ファイル操作時は[[Utilities/Documents/基本設計/基本設計#Markdownファイル処理ルール|基本設計]]を遵守する。
- ノートに追記・編集を行った場合は、Frontmatterの`updated`フィールドを実行日の日付（`YYYY-MM-DD`）に更新すること。
- インデント・改行コード・エンコーディングは`config.yaml`の`markdown_format`に従うこと（詳細は「箇条書きタグツリー解析・追記モジュール」の項を参照）。
### 複数ノートを結合して保存する
指定されたノート群の本文を1つに結合し、別のノートとして保存する処理を共通化する。**どのノートを対象とするか（収集条件）は呼び出し元のタスクが決定し、本機能はその結果（ノートパスの一覧）を受け取って結合するだけ**とする。
- `combine_notes(note_paths, output_path, frontmatter, exclude_tags=None, signature_field="source_signature")`
	- `note_paths`：結合対象ノートの相対パス一覧（呼び出し元がすでに条件で絞り込み済みのもの）
	- `exclude_tags`：各ノートの本文から、[[Utilities/Documents/詳細設計/共通設定・モジュール仕様#箇条書きタグツリー解析・追記モジュール（`markdown_tag_tree.py`）|箇条書きタグツリー解析・追記モジュール]]の機能を用いて配下ごと除外するタグ（例：`#メモ`）
	- `output_path`：結合結果の保存先パス
	- `frontmatter`：出力ノートに設定するFrontmatter（`type`・`aliases`等、呼び出し元が指定）
- 差分チェック：`note_paths`それぞれの相対パスと`updated`フィールドの値の組をソート・結合してシグネチャを計算し、`output_path`に既存ノートがあればそのFrontmatterの`signature_field`（既定：`source_signature`）と比較する。一致すれば書き込みをスキップし（スキップ理由をログに出力）、一致しなければ結合結果を書き込み、新しいシグネチャを`signature_field`に記録する。
## Frontmatter検証モジュール（`frontmatter_validator.py`）
ノートのFrontmatterについて、共通必須項目および、`project_type`、`type`ごとの必須項目、値の型、許容値を検証する。
Markdownファイルの構文解析と入出力は`markdown_io.py`が担当し、Frontmatterの意味上の妥当性検証は`frontmatter_validator.py`が担当する。
### 検証対象
- 必須フィールドの存在
- 値が空でないこと
- 値の型
- 許容値
- 日付書式
- ノート種別に応じた条件付き必須項目
- フォルダ配置とFrontmatterの整合性
- フィールド間の整合性
### 検証対象範囲
Frontmatterの必須条件検証は、本システムの処理対象として選定されたMarkdownノートに適用する。
Vault内のすべてのMarkdownファイルを無条件に検証するものではない。
タスクの探索条件外のノート、および除外フォルダ内のノートは、当該タスクの検証対象外とする。
ただし、除外フォルダであっても読み取りが許可され、かつタスクが明示的に参照対象として選定したノートについては、読み取りに必要な範囲で検証を行う。
### 呼び出し方針
- `markdown_io.py`はFrontmatterの構文解析後、共通項目の検証を呼び出す。
- `project_discovery.py`はプロジェクト管理ノートを取得した後、プロジェクト管理ノート固有の検証を呼び出す。
- `project_type`およびノートの`type`が確定した後、呼び出し元は`validate_note()`を用いて、`project_type`・`type`固有項目を含む検証を行う。
- タスクスクリプトは必須条件およびスキーマ選択ロジックを個別実装せず、必ず本モジュールを利用する。
### 検証インターフェース
- `validate_common(path, frontmatter)`
  - 全ノート共通項目を検証する。
- `validate_project_note(path, frontmatter)`
  - プロジェクト管理ノートの共通項目と固有項目を検証する。
- `validate_note(path, frontmatter, project_context)`
  - `project_type`および`type`から適用スキーマを決定し、共通項目とノート種別固有項目を一括検証する。
  - `project_context`には、所属プロジェクトの`project_type`、`project_name`、プロジェクトフォルダのパス、プロジェクト管理ノートのパス等、配置・リンク整合性の検証に必要な情報を渡す。
### 検証結果
検証関数は、少なくとも以下を返す。
- 検証の成否
- エラー一覧
- 警告一覧
- 情報メッセージ一覧
- 検証対象ノートのパス
- 適用した検証スキーマ
- 処理継続の可否
- 推奨する中断単位：`note` / `project` / `task`のいずれか
### 検証結果の重大度
#### ERROR
以下は処理対象から除外するエラーとする。
- 必須フィールドが存在しない
- 必須フィールドが存在するが、値が空である
- フィールドの型が不正である
- 値が許容値に含まれない
- 日付の書式が不正である
- ノートの`type`とフォルダ配置が矛盾する
- `project_link`と実際の所属プロジェクトが一致しない
- Frontmatterまたはフォルダ構成から対象ノートを一意に特定できない
- 書き込み対象ノートについて、安全な更新に必要な情報が不足している
#### WARNING
以下は原則として処理継続可能な警告とする。
- 推奨フィールドが存在しない
- 処理結果に影響しない任意フィールドに不整合がある
- 設定上の書式と既存ノートの書式が異なるが、既存ノートの書式を安全に踏襲できる
- 運用上の推奨条件を満たしていないが、必須条件および安全条件は満たしている
#### INFO
以下は情報として記録する。
- 省略可能なフィールドが未定義のため、仕様で定めた既定値を評価時に適用した
- 検証には成功したが、タスクの抽出条件に一致しなかった
- Frontmatterは正常だが、除外規則または実行条件により処理対象外となった
- 
省略可能なフィールドが存在しない場合と、フィールドが存在するが値が空である場合は区別する。
仕様で既定値が定義されている省略可能フィールドが存在しない場合は、Frontmatter自体を自動更新せず、評価時のみ既定値を使用してINFOを記録する。
一方、フィールドが存在するにもかかわらず値が空の場合は、不正値としてERRORとする。
### ノートが要件を満たさない場合の共通挙動
Frontmatterに不備があるノートは、自動補正せず、警告またはエラーをログに記録する。
ERRORがあるノートは処理対象から除外する。
WARNINGのみの場合は、警告内容が処理の安全性および結果に影響しないことを確認した上で処理を継続できる。
異常のあるノートが含まれていても、他の正常なノートの処理は継続する。
ただし、安全な処理継続ができない場合は以下のスコープの範囲で処理を中断する。
#### 異常時の処理単位
- プロジェクト管理ノートにERRORがある場合：当該プロジェクト全体を処理対象から除外する。
- 読み取り対象の通常ノートにERRORがある場合：原則として該当ノートのみを処理対象から除外する。
- 書き込み対象ノートにERRORがある場合：当該ノートへの書き込みを中止する。
- 転記先ノートにERRORがある場合：転記先への追記および転記元への転記済マーキングをいずれも行わない。
- 複数ファイル間の整合性を前提とする処理で、必要なノートを安全に特定できない場合：当該プロジェクトまたは当該タスク単位で中断する。
### Frontmatter検証条件の管理
Frontmatterの意味、必須条件、許容値に関する設計上の正本は、共通の[[Utilities/Documents/詳細設計/データ整理ルール|データ整理ルール]]、およびプロジェクトタイプ別の整理ルール（例：[[Utilities/Documents/詳細設計/データ整理ルール（執筆）|データ整理ルール（執筆）]]）とする。
初期実装では、これらの条件を`frontmatter_validator.py`内のスキーマとして実装する。

将来スキーマを設定ファイルへ外部化する場合は、実行設定との混在を避けるため、Frontmatter検証用の専用ファイルへ配置することを推奨する。
- 共通スキーマ：`config/schemas/common_frontmatter.yaml`
- `project_type`別スキーマ：`config/schemas/project_types/プロジェクトタイプ名_frontmatter.yaml`
スキーマの配置を変更する場合でも、`project_type_mapping`との対応関係を維持し、タスクスクリプトには検証条件を直接記述しないこと。
## 箇条書きタグツリー解析・追記モジュール（`markdown_tag_tree.py`）
インラインタグ付き箇条書きツリー構造（[[Utilities/Documents/詳細設計/データ整理ルール（執筆）|データ整理ルール（執筆）]]参照）を扱う処理を共通化する。
最低限、以下の機能を持つこと。
- 指定したノード（タグ）を起点に、配下の子・孫ノードを階層構造を保ったまま抽出する機能
- 指定したノード（タグ）を起点に、配下の全ノードを深さを問わず走査・列挙する機能（子ノードだけでなく、任意の階層にあるノードを検出する処理で使用する）
- 指定した階層の末尾（最後の子ノード）に、階層構造・インデントを保ったままブロックを追記する機能
- 指定したタグを含むノードを、配下ごと削除する機能
- 指定したタグのノードが存在するかを判定する機能（新規ツリー作成が必要かどうかの分岐に使用）
- ノード検索時、`#タグ`は前方一致ではなく完全一致で判定すること（例：`#1話`と`#1話目`を誤って一致させない）
- 指定したノードに、転記済マーキング（`#タグ ▶/◀ [[リンク]] へ/から #skip_tag`形式）を付与する機能

インデント・改行コードは`config.yaml`の`markdown_format`（`indent_style` / `tab_width` / `line_ending`）に従うこと。ただし既存ノートのインデントスタイルが設定値と異なる場合は、ノート内でスタイルが混在しないよう、既存ノートのスタイルを優先して踏襲すること。
## AI問い合わせモジュール（`ai_client.py`）
「AIへの問い合わせは最低限に留める」という方針を実装レベルに落とし込むための具体的な仕様を以下に定め、実装する。
### 1 呼び出し粒度の原則
AIへの問い合わせは、ノート単位・タスク実行単位でまとめて行い、同一実行内で同じ対象に対して複数回問い合わせない。
複数ノートを横断解析する必要がある場合も、可能な限り1リクエストにまとめること。
（例：複数日分のデイリーノートを走査するタスクにおいても、各日ごとにAIへ問い合わせるのではなく、抽出した候補ブロックをまとめた上で1回のリクエストに集約すること。）
### 2 ローカル処理優先・AIはフォールバック
自由記述セクションからのタグ抽出など、AI解析が必要になりがちな処理については、まずPythonによるローカル処理（正規表現・構造解析等）を試みる。
対象ノートが定められた軽量書式（各プロジェクトルールを参照）に従っている場合は、ローカル処理のみで完結させ、AIへの問い合わせを省略する。
書式に従っていない場合、または抽出結果が空になる場合にのみ、AIによる解析にフォールバックする。
（例：[[Utilities/Documents/詳細設計/データ整理ルール（執筆）|データ整理ルール（執筆）]]の「キャラクター一覧」「設定項目一覧」の書式）
### 3 AI出力形式の統一
判定・抽出系のAI問い合わせは、原則として**JSON形式での構造化出力**を指示し、自由文での応答を許可しない。
各タスクのプロンプトテンプレートには、期待するJSONスキーマを明記すること。
#### 例：タグ抽出タスクの出力スキーマ
```json
{
  "characters": ["アナスタシア", "シルヴィア"],
  "settings": ["世界設定", "資料"]
}
```
### 4 フォールバック規定（通信エラー・パース失敗時）
API通信タイムアウト、ネットワークエラー、またはパース不能なレスポンスが返却された場合は、**安全側に倒して処理（データの削除・移動を行わない`RELEVANT`扱い）**とし、ログに警告を出力して処理を継続する。**
### 5 プロンプトテンプレートの変数埋め込み方式
プロンプトテンプレート（`prompts/個別タスク名.txt`）へ、ノート本文などの自由記述テキストを埋め込む際は、Python標準の`str.format()`ではなく、以下の方式を用いること。
- テンプレート内のプレースホルダは、本文中に自然発生しない記号列（`%%トークン名%%`。例：`%%CONTEXT_TEXT%%`、`%%WORKING_TEXT%%`）で記述する。
- 埋め込みは`str.replace("%%トークン名%%", 値)`で行う。

`str.format()`を使わない理由は、埋め込む値がObsidianノートの自由記述本文であり、`{`や`}`を含む可能性を排除できないため（`str.format()`は本文中の`{`/`}`と衝突してエラーになりうる）。
XML風のタグ（`<reference_data>`等）でプロンプト内のセクションを区切ること自体は問題ない。プレースホルダの記法のみ上記に統一する。
## キャッシュモジュール（`cache.py`）
AI解析結果をキャッシュする場合、キャッシュキーには以下を含めること。
- 対象ノートの相対パス
- 対象ノートの`updated`フィールドの値（未設定時はファイルの最終更新日時で代替）
- プロンプトテンプレートのバージョン（テンプレート変更時にキャッシュを無効化するため）

`cache_ttl_days`（`config.yaml`の`ai.cache_ttl_days`）による日数ベースの失効に加えて、上記キーが変化した場合は`cache_ttl_days`内であっても再解析すること（内容が変わっているのに古いキャッシュを使い続けないため）。
## Wikilink構築モジュール（`wikilink.py`）
ノートへの参照リンク（Wikilink）を生成し、出力する。
- フォーマットは、`config.yaml`の`markdown_format.wikilink_style`の指定に従う。
	- `full_path_no_ext`：Vaultルートからのフルパスから拡張子（`.md`）を除いた形式（例：`[[今世は悪女/Settings/シルヴィア]]`）
	- （今後、別形式が必要になった場合はこの一覧に追記すること）
- リンク生成時、パス区切り文字はOS依存にせず`/`に統一する。
## スナップショット・バックアップモジュール（`snapshot.py`）
1. 編集対象となるファイルは、書き換え直前に`snapshots/YYYY-MM-DD/`配下へ、Vaultのディレクトリ構造を維持したままコピー保存する。
2. 設定された保持期間（`backup.retention_days`）を過ぎた古いスナップショットおよびログは、実行時に自動削除する。
3. `.venv`、`snapshots`、`logs`、`cache`、`.env`はVault内にあってもOneDrive等の同期・管理からは除外設定（または`.gitignore`／除外フォルダ登録）を行う。
4. `run.mode: dry_run`の場合はスナップショット取得・書き込みともに行わない（[[Utilities/Documents/基本設計/基本設計#実行モード（dry_run / execute）の共通挙動|実行モード（dry_run / execute）の共通挙動]]参照）。
