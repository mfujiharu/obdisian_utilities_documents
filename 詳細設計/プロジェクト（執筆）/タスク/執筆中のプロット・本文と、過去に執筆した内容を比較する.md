# タスクの概要
本タスクは`project_type: 執筆`用のタスクである。
執筆中のプロット・本文と、過去に執筆した（作業完了した）プロット、本文、設定を比較するための文脈資料（コンテキストノート）を用意し、AI（Gemini Scribe）との対話を通じて矛盾点等のコメントを得られるようにする。
# 前提条件
本タスクは、
- Gemini Scribe（Obsidianのコミュニティプラグイン。[[Utilities/Documents/詳細設計/Python実行環境・AIエージェント情報|Python実行環境・AIエージェント情報]]参照）
- Pythonスクリプト

を併用して実装する。

Pythonスクリプトの実行環境、前提条件、基本ルールは、[[Utilities/Documents/基本設計/基本設計|基本設計]]を参照のこと。

本タスクのうちPythonスクリプトが担うのは、後述「整理・抽出手順」（コンテキストノートの生成）のみである。この工程は通常のバッチ処理として`main.py --task coherence_check`から実行し、CLIエントリーポイント・実行モード（dry_run/execute）・スナップショット規定など、開発ルールの共通ルールに従う。

生成後にGemini Scribeで行う対話（後述「Gemini Scribeでの問い合わせ方法」）は、ユーザーがその場で行う対話的な作業であり、[[スポット/Pythion開発/（旧）共通設定・モジュール仕様#AI問い合わせモジュール（`ai_client.py`）|AI問い合わせモジュール]]の各規定（呼び出し粒度の原則・JSON出力形式の統一・フォールバック規定・キャッシュ）の対象外とする。
# タスク名
本個別タスクのタスク名は「**coherence_check**」とする。
# 本タスク用設定ファイル
本タスク用の設定ファイルには、以下を記述する。
（ファイルパス：`config/tasks/coherence_check.yaml`）
```
coherence_check:
  use_ai: false
  artifact:
    type: "ai_context"
    schema_version: 1
    signature_version: 1
    generator_version: "1"
  context:
    max_file_bytes: 5000000
    max_source_count: 500
    on_limit_exceeded: "split"
    split_strategy: "type"
    preserve_source_boundary: true
    index_file: "コンテキスト.md"
    manifest_file: "コンテキスト.manifest.json"
    part_filename_pattern: "{stem}_{group_order:02d}_{group_label}_{part_number:03d}.md"
```
# 整理・抽出手順
## 1. 設定ファイルの読み込み
## 2. 対象プロジェクトの抽出
[[スポット/Pythion開発/（旧）共通設定・モジュール仕様#プロジェクト探索モジュール（`project_discovery.py`）|プロジェクト探索モジュール]]の`find_projects()`を用い、以下を満たすプロジェクトを検出する。
- `project_type: 執筆`
- `status: true`
- `ai_check: true`

同時に **プロジェクト名（=`project_name`）** を取得する。
## 3. 集約対象ノートを選定する（本タスク固有の条件）
以下の条件でノートを選定する。この選定条件は本タスク固有であり、モジュール側には持たせない。
- プロジェクト管理ノート：無条件で含める
- 設定ノート：`Settings/`内の全ノート
- 作業ノート：[[スポット/Pythion開発/プロジェクトタイプ（執筆）設定・モジュール仕様#作業ノートの検出|プロジェクトタイプ（執筆）設定・モジュール仕様]]の「作業ノートの検出」に、プロジェクト名・（ノート名は空欄）・`status: false`を渡して検出したもの
- プロットノート：`final: true`のもの
- 本文：`final: true`のもの
## 4. ノートを結合し、コンテキストノートとして保存する
`combine_notes()`を用い、`artifact_type: ai_context`の結合成果物として保存する。選定条件、`#メモ`除外、相対パス昇順、出典境界付与を`build_options`へ渡す。
- 通常時：`Temp/コンテキスト.md`へ本文を保存し、`artifact_role: single`とする。
- 分割時：`Temp/コンテキスト.md`を`artifact_role: index`の索引とし、各partを独立成果物として保存する。
### 分割条件
変換後のUTF-8バイト数または原本数が上限を超えた場合に分割する。除外・整形・出典付与後の実出力サイズで判定する。原本1ノートの途中分割は禁止し、単一原本だけで上限超過する場合はERRORとして既存成果物を変更しない。
### 分割グループ
1. 概要：プロジェクト管理ノート
2. 設定：設定ノート
3. 構成：全体構成ノート・作業ノート
4. プロット：プロットノート
5. 本文：本文
未定義の`type`があれば自動的にその他へ入れずERRORとする。グループ内はVault相対パス昇順を維持し、上限を超える直前で次partへ送る。
### ファイル名
`{stem}_{group_order:02d}_{group_label}_{part_number:03d}.md`とする。例：`コンテキスト_02_設定_001.md`。
### シグネチャとFrontmatter
各partは`artifact_role: part`と個別`source_signature`を持つ。indexはpartの相対パスと各シグネチャから全体シグネチャを算出する。共通項目として`artifact_type`、`artifact_role`、`artifact_schema_version`、`source_signature_version`、`source_signature`、`generator_version`、`generated_at`、`source_count`を記録する。
### マニフェスト
`Temp/コンテキスト.manifest.json`を全体マニフェストとして1ファイル生成し、index、part、分割条件、原本一覧を記録する。partごとの個別マニフェストは作成しない。
### 原子的更新
全分割計画と一時ファイルを先に生成・検証し、既存成果物のスナップショット取得後に正式ファイルへ置換する。失敗時は既存成果物を変更しない。
### 過去の不要part
再生成後に不要になった旧partは自動削除しない。現行マニフェストに記載されたファイルだけを有効とし、不要候補をWARNINGへ記録する。
# Gemini Scribeでの問い合わせ方法
Gemini Scribeのチャット画面から以下のプロンプトで問い合わせる。

例：
```
@Active File と @プロジェクト名　を比較して、矛盾点を指摘して
```

プロンプトはユーザがタスクに応じてその場で書くので（あるいはGemini Scribeに定型文として登録するので）、スクリプトで作成はしない。
